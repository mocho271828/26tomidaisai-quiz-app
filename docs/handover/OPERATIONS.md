# 当日の運用と障害対応

この手順は現行mainの実装・設定に基づきます。
2026年に本番使用した版・人数・全機能の確認結果は未特定のため、次年度は使用版で実機リハーサルを行ってください。
アプリを操作する担当者と、AWS・DB・DNSを管理する担当者を事前に決めます。

## 開催前

1. 問題・正解・順番・通常の終了位置・予備問の使用条件を確認する。現行は練習1問＋本番5問、予備2問。
2. 使用commit、image digest、問題JSON、採点・時間・表示設定のsnapshotを記録し、全APIとFrontendを対応する版へ揃える。
3. 参加者、運営、司会者の実端末で、HTTPS/WSS、登録、回答、集計、結果公開、次問、終了・表彰まで確認する。
4. 順位・分布の公開予定を司会と合わせる。現行は分布が初期表示、本人順位・全体順位が初期非表示で、いずれも手動切替。
5. backupの保存先・鍵の管理者と、障害時に確認するログ・CloudWatch Dashboardを確認する。
6. 不要なBrowser Runnerを停止する。試験を行う場合は予定問数を通常6問または予備込み8問へ明示設定する。

実際に配信した先頭1問が練習です。運営画面で問題順を変えると練習に使う問題も変わります。
DBの設定はJSONの編集だけでは更新されません。[開催設定](../QUIZ_CONFIGURATION.md)と[問題設定](../QUESTION_CONFIGURATION.md)を確認してください。
順位の表示設定が混在している場合、順位ボタンは両方公開へ揃えるため、非公開にしたい順位を誤って公開しないよう事前に確認します。

## 司会者画面の扱い

`/moderator`は運営認証を共用します。
画面に進行ボタンはありませんが、専用のread-only権限ではないため、資格情報は運営権限を持つものとして管理してください。
埋込画面は通常の参加者画面で、同じブラウザの参加者セッションを使い、未登録なら自動参加を試みます。参加が成立すると、閲覧だけでも実参加者として人数に含まれ、回答・得点も通常参加者と同様に集計されます。
司会者のTOP5は運営認証下で最新の確定結果を表示するため、参加者への結果・表彰公開とは分けて扱います。

## 各問の進め方

1. 運営が問題文・選択肢・正解を確認し、問題を確定・配信する。
2. 開始を予約する。現行の開始待ちは3秒。
3. 参加者が開始から10秒未満で選択する。到着猶予4秒の後、集計完了の`ReadyToReveal`を待つ。
4. 運営が集計結果を確認し、司会の合図で「正解・結果を公開」を押す。時間経過だけでは公開されない。
5. 参加者の結果と順位の公開範囲を確認する。
6. 「次の問題へ進む」または「Event終了」の確認を行う。Round backupの作成・復号・照合が成功した場合だけ進行する。

現行採点は正解400点＋回答速度に応じた最大100点で、練習は総合得点に含めません。
5問終了で自動終了する機能はなく、公開後に運営が終了を選びます。

## 最終問題と表彰

1. 最終問題の集計後、司会の合図で正解・結果を公開する。
2. 参加者が正解を確認した後、「Event終了」の確認操作を行う。参加者は「最終結果発表!!」の待機画面になる。
3. 司会の発表に合わせ、「表彰対象者を呼び出す…」から「呼び出し・最終ランキングを一斉公開」を確定する。
4. 表彰後、「アンケート・ホームページ案内へ…」から案内表示を確定する。

対象は総合5位以内の全員です。同率により5人を超えることがあるため、ページ切替で全員を確認します。
表彰公開から待機へ、案内から表彰へ戻る操作はありません。
アンケート・ホームリンクはbuild時に設定されたものだけが表示されます。[年度変更箇所](README.md#年度が変わるときに確認する場所)

## 障害時に最初に行うこと

| 症状 | 確認と対応 |
| --- | --- |
| 運営操作の応答が不明 | 最新状態を確認する。同じ操作の再送には既存の同じ冪等keyを使い、連打しない |
| 版の競合 | 現在の状態を取得し直し、既に反映されていないか確認する |
| 集計が`VoidCandidate` | 固定の失敗コードを確認し、原因解消後に専用の「結果集計を再試行」を使う |
| 次問・終了へ進めない | backup作成・復号・照合の失敗を確認する。失敗を無視して次Roundを作らない |
| 参加者の画面が更新されない | 接続、最新状態、時刻再同期を確認する。タブ復帰後は同期完了まで回答が無効になる |
| AWS workflowが失敗・中断 | Summaryと固定診断を確認する。DBが変更前か変更後かを終了状態だけで決めない |

復旧目的でDeploy、Reset Event、Destroyを選ぶ前に、対象と失われるデータを管理者が確認します。
Event Status失敗時にDeploy updateを実行すると、調べたい開催を削除してしまいます。
AWSの配置途中失敗やDNS競合は、同じcreateの連続実行で解消しようとせず、[AWSの障害対応](../GITHUB_ACTIONS_AWS.md)に従います。
ログを共有するときは、Cookie、CSRF、パスワード、鍵、実参加者データを含めません。

## AWS操作の違い

以下は専用`aws-review`環境の手動workflowです。操作前に[正式な手順](../GITHUB_ACTIONS_AWS.md)で対象・権限・入力値を確認します。

| 操作 | データ・環境への影響 |
| --- | --- |
| AWS Review Event Status | 現在のEvent UUID・version・状態を読み取る |
| AWS Review Deploy `create` | 新規専用環境を作成し、DBを初期化して現在の問題・設定から新Eventを作る |
| AWS Review Deploy `update` | 既存環境を更新し、**専用DBを全初期化**して新Eventを作る。機種と公開入口はworkflow入力に従う |
| AWS Review Reset Event | Event UUID・問題・静的設定・採点policy・ID sequenceを保持し、参加者・回答・得点・進行を削除する |
| AWS Review Destroy | 専用AWS資源、DB、Round backup、Reset archiveを削除する |

**Deploy updateも既存開催のデータを失うため、開催中に配置しないでください。**
Reset Eventは配置済みsourceとmainの一致、期待Event UUID・versionの確認が必要です。
Reset後は運営の再ログインと参加者の再参加が必要で、旧参加者IDは再利用しません。
Resetのarchive検証後に失敗した場合も、自動再reset・自動rollback・自動再起動は行われません。
GitHub Actionsの待機中実行が置き換わる場合があるため、workflowを連打せず結果を確認します。

## backupの範囲と開催終了後

Round backupは各問の回答・得点・集計を保全するもので、開催全体の設定・表彰段階まで復元するものではありません。
Reset Eventの暗号化archiveは別形式ですが、作成・復号照合の成功は別DBへの復元検証成功を意味しません。
元の開催へ戻すボタンや自動復元機能はなく、復旧には別途設計・承認・検証が必要です。
どちらも環境内にあるデータはDestroyで消えるため、必要な記録の保管方法を削除前に管理者が決めます。

1. 本番日時、使用版、問題・設定、参加人数、障害と対応、実施できなかった確認を記録する。
2. 必要なデータと鍵の保管先・保存期限・削除責任者を非公開で引き継ぐ。
3. AWS資源を終了する場合は、対象と削除範囲を確認してDestroyを実行し、各サービスの削除結果を確認する。
4. 公開DNS、外部管理の証明書、OIDC/IAM等の残存と管理者を確認する。Destroy成功だけでアカウント全体の課金停止とは判断しない。

`aws-review`は`EnableDeadline=false`で、期限による自動撤去は無効です。
workflowの失敗、手動キャンセル、180分timeoutでも自動削除されず、撤去完了まで稼働・課金が続きます。
削除APIの受付と撤去完了を区別し、[撤去手順](../GITHUB_ACTIONS_AWS.md#確認が終わったら撤去する)に結果を照合してください。
